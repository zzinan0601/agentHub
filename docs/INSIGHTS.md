# Dashboard 읽는 법

상단 띠의 **Dashboard** 로 들어간다. 로그인만 하면 누구나 볼 수 있다.
각 개발자가 자기 에이전트가 잘 쓰이는지 알아야 고칠 수 있기 때문이다.

기간은 오늘 / 7일 / 30일 / 전체 중에서 고른다. 화면 전체에 걸린다.

---

## 이 화면이 답하려는 질문

1. 사람들이 무엇을 묻고 있나
2. 내 에이전트가 쓰이고 있나, 느리지 않나
3. **다음에 어떤 에이전트를 만들어야 하나**

3번이 가장 중요하다. 아래 "에이전트 미호출 질문" 이 그 답을 준다.

---

## 점검 대상

문제가 있는 에이전트만 위쪽에 모아 둔다. 여기가 비어 있으면 나머지는 대충 봐도 된다.

| 표시 | 뜻 | 할 일 |
| --- | --- | --- |
| **이 기간에 한 번도 안 불림** | 라우터가 이 에이전트를 고르지 않았다 | `manifest.yaml` 의 `description` 을 구체적으로 다시 쓴다. 무엇을, 어떤 기간·단위로, 어떤 형태로 주는지. `examples` 도 2개 이상 넣는다 |
| **응답 없음** | `/health` 가 답하지 않는다 | 노트북이 꺼졌거나 방화벽. 다른 PC 에서 `curl <내IP>:<포트>/health` |
| **계약 버전 다름** | `contract.py` 가 옛날 복사본 | `python scripts/sync_contract.py` 결과로 덮어쓴다 |
| **실패율 N%** | `.env` 의 `INSIGHT_FAIL_RATE_WARN`(기본 20%)를 넘었다 | 표의 마지막 호출 시각을 보고 그 시점 로그를 확인한다 |
| **registry.yaml 에서 빠짐** | 호출 기록은 있는데 지금은 등록돼 있지 않다 | 의도한 것이면 그대로 둔다. 실수면 다시 등록한다 |

## 에이전트별 활용

| 열 | 읽는 법 |
| --- | --- |
| 호출 / 실패 | 기간 내 횟수. 실패는 비율도 함께 |
| 평균 | 성공한 호출의 평균 응답 시간 |
| **p95** | 100번 중 95번은 이 시간 안에 끝났다는 뜻. **평균만 보면 가끔 튀는 호출이 묻힌다** |
| 최대 | 가장 오래 걸린 한 건 |
| num_ctx | 에이전트가 **실제로 쓴** 컨텍스트 크기의 평균 |

**"느린 순" 으로 정렬하면 병목이 바로 보인다.** 평균은 멀쩡한데 p95 가 크게 벌어지면
특정 조건에서만 느려지는 것이니 그 조건을 찾는다.

### num_ctx 로 설정 조정하기

이 값은 `.env` 를 근거 있게 고치라고 있는 것이다.

- 평균이 `NUM_CTX_MIN` 에 붙어 있다 → 하한이 과하게 크다. 낮추면 메모리를 아낀다.
- 최대가 `NUM_CTX_MAX` 에 자주 닿는다 → 프롬프트가 잘리고 있을 수 있다.
  `CHARS_PER_TOKEN` 이 실제보다 크게 잡혀 있다는 뜻이므로 값을 낮춰(예: 2.0 → 1.7) 다시 본다.
- 칸이 비어 있다 → 그 에이전트는 LLM 을 쓰지 않는다. 정상이다.

## 선택 방식

| 값 | 뜻 |
| --- | --- |
| 자동 선택 | 사용자가 아무것도 안 골라 코디네이터 LLM 이 판단했다 |
| 사용자 지정 | 화면에서 에이전트를 직접 체크했다 |
| 워크플로우 | 정해진 순서로 돌았다 |

자동 선택 비율이 낮고 사용자 지정이 대부분이라면, 사람들이 라우터를 믿지 못하고 있다는 뜻이다.
`manifest` 설명이 부실하거나 `core/prompts/router.md` 를 손볼 때다.

## 에이전트 미호출 질문

라우터가 후보를 하나도 고르지 않아 코디네이터가 직접 답한 경우다. 예시 질문이 함께 나온다.

- 인사·잡담이면 정상이다.
- **업무 질문인데 여기 쌓인다면 그 일을 하는 에이전트가 없다는 뜻이다.**
  다음에 만들 에이전트를 이 목록에서 고르면 된다.

## 자주 묻는 질문

**말끝만 다른 질문은 하나로 센다.** "지점별 매출 알려줘" 와 "지점별 매출 알려주세요" 는
같은 질문으로 묶인다. 그대로 세면 같은 질문이 표현마다 쪼개져 무엇이 자주 묻는 질문인지
드러나지 않기 때문이다.

묶는 기준은 `.env` 의 `INSIGHT_SIMILARITY`(기본 0.8)다. 비교하기 전에 요청 어미
("~줘", "~주세요")를 떼므로 뜻이 반대인 "매출 올려줘 / 매출 내려줘" 는 갈린다.
기준을 바꿨다면 `python scripts/test_similar.py` 로 경계가 무너지지 않았는지 확인한다.

한 줄에 붙는 것들:

| 표시 | 뜻 |
| --- | --- |
| 앞의 숫자 | 이 질문이 몇 번 나왔는지 |
| 에이전트 칩 | 이 질문에 주로 불린 에이전트 |
| `gemma4:31b 2.3s ×5` | **그 모델로 몇 번 물었고 평균 몇 초 걸렸는지.** 크기(12b/e4b/e2b)까지 나오므로 같은 계열의 다른 크기도 구분된다 |
| 표현 N가지 | 실제로 쓰인 문장이 몇 가지였는지 |

모델이 둘 이상 붙어 있으면 **같은 질문을 서로 다른 모델로 던진 결과**다. 같은 일을 시켰으니
그 숫자를 그대로 비교하면 된다. 폐쇄망에 모델을 새로 올렸을 때 쓸 만한지 판단하는 근거가 된다.

## 최근 질문

질문 한 줄마다 호출된 에이전트가 칩으로 붙고, 어떤 모델로 답했는지와 소요 시간이 나란히 붙는다.
실패한 에이전트는 빨간 칩이다. `예약` 칩은 스케줄이 대신 던진 질문이다.

## 사용자별 활용

누가 얼마나 쓰는지 본다.

> 로그인을 도입하기 전에 쌓인 기록은 사람이 붙어 있지 않아 이 표에서 빠진다.
> 위쪽 요약의 호출 수와 차이가 나는 것은 그 때문이며, 시간이 지나면 저절로 맞아간다.

## 숫자가 이상해 보일 때

| 증상 | 이유 |
| --- | --- |
| 사용자별 호출 합 < 요약 호출 수 | 로그인 도입 전 기록에는 사람이 없다 |
| num_ctx 가 비어 있다 | 그 에이전트가 LLM 을 쓰지 않는다 |
| 실패율은 0인데 호출이 많다 | 정상이다. 잘 돌고 있다는 뜻 |
| "오늘" 과 "전체" 가 같다 | 아직 오늘 것밖에 없다 |
| 어떤 에이전트가 목록에 아예 없다 | `registry.yaml` 에 없고 호출 기록도 없다 |
