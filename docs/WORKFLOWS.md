# 워크플로우 - 호출 순서를 고정하기

평소에는 코디네이터 LLM 이 질문을 보고 어떤 에이전트를 부를지 정한다. 대부분은 이게 편하지만,
**매번 똑같이 돌아야 하는 작업**에는 맞지 않는다. 로컬 모델의 판단은 매번 조금씩 달라지기
때문이다. 워크플로우는 그 판단을 아예 건너뛰고 정해진 순서만 실행한다.

이런 때 쓴다.

- 매일 아침 같은 형식의 점검 보고서가 필요할 때
- 여러 부서 데이터를 **항상 같은 순서로** 모아야 할 때
- 스케줄과 묶어서 사람 없이 돌릴 때

---

## 1. 만들기

**화면에서 만드는 것이 기본이다.** 오른쪽 패널 아래 **워크플로우** 항목을 펼치고
`워크플로우 관리` 를 누르면 편집기가 열린다. 왼쪽에서 고르면 **그 파일의 원문이 그대로**
보이고, `＋ 새 워크플로우` 를 누르면 본보기가 채워진 채 시작한다.

```yaml
# 이 워크플로우가 왜 필요한지 여기에 적어두면 다음 사람이 이해합니다.

name: 일일 점검
description: 매일 아침 상태를 확인하고 요약 보고서를 만든다.
mode: sequential # parallel 또는 sequential
steps:
  - agent: echo
  - agent: summary
```

| 항목 | 의미 |
| --- | --- |
| 파일 이름 | 내부 키가 된다. **영문 소문자·숫자·하이픈**만 쓸 수 있다 |
| `name` | 화면 목록에 보일 이름 |
| `description` | 설명. 지금은 목록에만 쓰인다 |
| `mode` | `sequential` 이면 앞 결과를 다음 에이전트의 `upstream` 으로 넘긴다. `parallel` 이면 동시에 부른다. **어느 쪽이든 각 단계의 결과가 모두 답변에 남는다** |
| `steps` | 부를 순서. `agent` 값은 `registry.yaml` 의 `id` 와 같아야 한다 |

폼이 아니라 원문을 그대로 고치게 한 이유는, **왜 이 순서인지가 주석에 적히기 때문**이다.
폼으로 받으면 주석이 사라지고 파일을 직접 고치는 사람과 화면으로 고치는 사람이 서로 다른
것을 보게 된다. 대신 저장하기 전에 서버가 검사한다.

| 판정 | 조건 |
| --- | --- |
| **오류** (저장 막힘) | yaml 문법이 깨짐 · `steps` 가 없거나 비어 있음 · 단계에 `agent` 가 없음 · `mode` 가 `parallel`/`sequential` 이 아님 · `registry.yaml` 에 **없는** 에이전트 id |
| **경고** (저장은 됨) | 그 에이전트가 지금 **오프라인** · `name` 이나 `description` 이 없음 |

없는 id 를 오류로 두는 것은 `registry.yaml` 에 없으면 영영 부를 수 없기 때문이고,
오프라인을 경고에 두는 것은 담당자 노트북이 잠깐 꺼져 있을 뿐일 수 있기 때문이다.

편집기에서 <kbd>Tab</kbd> 은 두 칸 들여쓰기로 들어간다. yaml 은 들여쓰기가 곧 문법이다.

### 고치기와 지우기

- 워크플로우는 **전원이 함께 쓰는 공용 파일**이다. 누구나 고칠 수 있고, 저장하면 서버가
  맨 윗줄에 `# 마지막 수정: 이름 · 시각` 을 남긴다. 이 줄은 저장할 때마다 갱신된다.
- 두 사람이 같은 파일을 열어 두었다가 나중 사람이 저장하면 거부된다.
  창을 닫고 다시 열어 상대의 변경 위에 다시 고친다.
- **쓰고 있는 대화방이 하나라도 있으면 지울 수 없다.** 그 방들의 워크플로우를
  `사용 안 함` 으로 되돌린 뒤에 지운다.

### 파일을 직접 놓아도 된다

`core/workflows/` 에 yaml 파일 하나를 놓으면 그게 워크플로우 하나다. 화면에서 저장하는 것과
같은 일이다. 코어는 이 폴더를 **매 호출마다 다시 읽으므로** 어느 쪽이든 재기동이 필요 없다.

`.env` 의 `WORKFLOW_EDIT_ENABLED=false` 로 두면 화면에서는 보기만 되고 파일로만 고칠 수 있다.
폐쇄망 반입본을 잠가둘 때 쓴다.

## 2. 화면에서 고르기

오른쪽 패널 아래 **워크플로우** 항목을 펼쳐 목록에서 고른다.
고르면 그 대화방은 계속 그 순서로만 돈다.

- 에이전트 체크박스는 **잠긴다.** 순서를 워크플로우가 정하기 때문이다.
- 실행 방식(병렬/순차)도 워크플로우의 `mode` 를 따른다.
- 상단 제목 옆 칩에 `워크플로우 · 일일 점검` 이라고 표시된다.
- 해제하려면 다시 **사용 안 함** 을 고른다.

## 3. 질문 던지기

워크플로우를 골랐어도 질문은 평소처럼 입력한다. 그 질문이 각 단계의 에이전트에게
`query` 로 그대로 전달된다. 즉 **순서는 고정이고 내용은 매번 다를 수 있다.**

```
오늘 상태 점검해줘
```

답변 위 실행 트레이스에 이유가 `워크플로우 '일일 점검'` 으로 표시되고,
라우팅 LLM 호출이 없으므로 그만큼 응답도 빨라진다.

## 4. 스케줄과 함께 쓰기

워크플로우의 진가는 스케줄과 묶을 때 나온다. 같은 대화방에서:

1. 워크플로우를 고른다
2. 스케줄에 `0 9 * * 1-5` 와 질문을 넣는다 (→ [스케줄 문서](SCHEDULE.md))

그러면 평일 오전 9시마다 **항상 같은 순서로** 실행되고 결과가 그 방에 쌓인다.
사람이 매번 판단에 기대지 않아도 되므로 결과 형식이 일정하다.

## 자주 하는 실수

| 증상 | 원인 |
| --- | --- |
| 목록에 안 나옴 | 파일이 `core/workflows/` 밖에 있거나 확장자가 `.yaml` 이 아님 |
| 저장 버튼이 안 눌림 | 편집기 아래 빨간 줄을 본다. 오류가 하나라도 있으면 잠긴다 |
| "다른 사람이 먼저 고쳤습니다" | 그 사이 누가 같은 파일을 저장했다. 창을 닫고 다시 연다 |
| 지울 수 없음 | 그 워크플로우를 쓰는 방이 남아 있다. 안내 문구에 몇 개인지 나온다 |
| "부를 수 없습니다" 오류 | `steps` 의 `agent` 가 `registry.yaml` 의 `id` 와 다르거나 그 에이전트가 꺼져 있음 |
| 앞 결과가 안 넘어감 | `mode` 가 `parallel` 이다. 이어받게 하려면 `sequential` |
| 에이전트를 못 고르겠음 | 워크플로우 사용 중이라 잠긴 것이다. **사용 안 함** 으로 되돌린다 |
